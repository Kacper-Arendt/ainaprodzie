# The chat talks to models through Spring AI's OpenAI client and a LiteLLM proxy

The chat uses Spring AI 2.x (the line built for Spring Boot 4) and only its OpenAI model integration, with `base-url` pointing at a LiteLLM proxy that runs next to PostgreSQL in `compose.yaml`. Model access through LiteLLM is an external requirement, so the proxy stays even where a single provider would not need it.

LiteLLM holds the provider keys, which come from the environment (exported, or in a gitignored `.env` that Docker Compose reads) and never from the repository, and it maps a model alias to a real provider model. The app names only that alias. Every environment brings its own key, possibly for a different provider. The committed `config.yaml` points the default alias at Gemini (`GEMINI_API_KEY`), adds `chat-anthropic` for Claude (`ANTHROPIC_API_KEY`) and lists a commented entry for a local model. Moving to another provider means switching the alias's entry, or choosing another alias on the Settings page, and setting that provider's key, with no change to the code or the dependencies.

The app calls LiteLLM with a virtual key of its own, never with the master key. The key names the aliases the app may call (the access group `app` in `config.yaml`), a daily budget and a rate limit, and LiteLLM records what it spends. A key is a row in LiteLLM's database, not an entry of `config.yaml`, so in development the `litellm-app-key` service of `compose.yaml` creates it, or brings it in line with `litellm/app_key.py`, before the app starts, and the app's `dev` default names it. LiteLLM keeps its tables in a `litellm` schema of the app's PostgreSQL, apart from the app's. The models stay in `config.yaml`, not in that database. The LiteLLM image is pinned to an exact version, because the project releases very often.

The model has no tools: it answers from the system prompt, the conversation and the context block alone (chat ADR 0008). A question is one operation: the user is looked up once when it arrives, and the context block names that user, so a user disabled mid-question finishes it and is refused the next one. Regular tests replace the `ChatModel` with a stub, so `./mvnw verify` needs neither LiteLLM nor a key.

## Considered Options

- **The master key in the app.** This was rejected because the master key creates and deletes keys and calls every alias with no budget, so a leak of the app's configuration would hand out all of it.
- **The app's key in `config.yaml`.** LiteLLM 1.106 reads no virtual keys from its config file, so a key has to be created through its API, as `app_key.py` does.

## Consequences

- In production the master key stays with the administrators, and the app's key is created once, with the requests of `app_key.py` or in the admin UI, and reaches the app as the secret `LITELLM_KEY`. LiteLLM gets a database of its own, and LiteLLM instances behind one load balancer share a Redis, or each counts the rate limit on its own.
- An alias the app calls but the access group misses answers 403, which the chat shows as a failure. `AppKeyAccessGroupTests` keeps every alias in the group, so a merge forward that adds an alias without the group fails `./mvnw verify`. A spent budget answers 422, also a failure, until the budget resets at midnight UTC.

- Every provider other than OpenAI is reached through LiteLLM's OpenAI emulation. Streaming goes through that translation and is where provider quirks show up, and provider-specific features (Gemini's thinking settings, grounding, context caching) are out of the app's reach. One that LiteLLM can add on its own goes into the alias's entry in `config.yaml`, as Anthropic's cache marker does (chat ADR 0008).
- LiteLLM treats a request as Gemini only when the alias name contains `gemini`. Under any other alias it strips Gemini's thought signatures from the tool-call ids it hands back, and Gemini 3 then answers with weaker reasoning and no error. The chat calls no tools yet, but the alias is named for the tools that come later. The committed alias is therefore `chat-gemini`. Support staff choose the alias on the Settings page from `retrofit.chat.models`, and the choice is stored with the other chat settings, so switching provider needs no restart; an alias missing from that list cannot be chosen, and one missing from `config.yaml` or the access group fails the next question.
- Spring AI 2.x's OpenAI integration retries inside the openai-java SDK (`spring.ai.openai.max-retries`), not through `spring.ai.retry.*`, and LiteLLM retries a failed provider call again on its own. The two layers multiply, so a free-tier key can spend its daily quota on retries of one rate-limited question. LiteLLM gives each provider call 15 seconds and retries it once, rate limits included; the SDK waits 35 seconds per call, longer than LiteLLM's call and its retry, and retries once, so a rate-limited question reaches the provider up to four times. The 35 seconds hold the SDK's retry too: against a provider that answered after 20 seconds, LiteLLM cut its two attempts and answered 408 after about 31 seconds, the SDK retried, and the question ended with `timeout` 35 seconds after it was asked. The turn's deadline (70 seconds, chat ADR 0004) bounds every model call of a question together.
- Spring AI 2.x is recent, and most examples online are for 1.x, whose API differs. Use the 2.x reference.
